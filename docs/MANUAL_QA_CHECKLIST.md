# Manual QA and demonstration checklist

Use a fresh, disposable data directory and fictional records. Record the result and any observed issue; do not claim a scenario passed unless you ran it.

## Environment and baseline

- [ ] Pull the latest `main` branch.
- [ ] Configure: `cmake -S . -B build`.
- [ ] Build: `cmake --build build --config Debug`.
- [ ] Run tests: `ctest --test-dir build -C Debug --output-on-failure`.
- [ ] Confirm all 11 registered CTest entries pass: common, security, storage, auth, patient, doctor, appointment, billing, report, cli, integration.
- [ ] Launch the executable generated by the selected CMake generator.

## Authentication and authorization

- [ ] On an empty data directory, register the first administrator.
- [ ] Log in with the new administrator credentials.
- [ ] Attempt a wrong password; login must fail without entering protected modules.
- [ ] Log out; protected modules must require authentication again.
- [ ] As Admin, inspect user accounts and their enabled/disabled status.
- [ ] Disable a separate test account; verify it cannot log in afterwards.
- [ ] Verify the application refuses to disable the currently logged-in administrator.
- [ ] Verify the application refuses to disable the last active administrator.
- [ ] As Receptionist, verify patient, appointment, and billing modules are available.
- [ ] As Receptionist, verify Admin-only doctor administration and reports are unavailable.
- [ ] As Doctor, verify the general appointment module is denied until per-doctor profile scoping exists.
- [ ] Do not claim Patient self-service or Doctor personal schedule functionality; these are documented SRS gaps.

## Patient and doctor records

- [ ] Create a fictional patient with valid required fields.
- [ ] Search for the patient by ID.
- [ ] Search by a partial/case-insensitive name if supported by the menu.
- [ ] Update a patient field and verify the changed value.
- [ ] Attempt a duplicate or malformed patient input and record the actual validation response.
- [ ] As Admin, create a fictional doctor with a valid working-hours range.
- [ ] Update the doctor and verify the new details.
- [ ] Check the doctor's availability representation.

## Appointments

- [ ] Book an appointment for the test patient and doctor in an available slot.
- [ ] Attempt a second appointment for the same doctor and time; the conflict must be rejected.
- [ ] Cancel a test appointment and verify its status.
- [ ] Reschedule an appointment to a free slot.
- [ ] Attempt to reschedule into an occupied slot and verify the conflict is rejected.

## Billing and reports

- [ ] Create an invoice for the test patient.
- [ ] Verify the displayed total and outstanding amount.
- [ ] Change the payment status using the available workflow.
- [ ] Verify the report output reflects the test patient/appointment data.
- [ ] As a non-admin role, verify reports are not accessible.

## Persistence and cleanup

- [ ] Exit normally.
- [ ] Restart using the same data directory.
- [ ] Verify the test patient, doctor, appointment, invoice, and user records persist.
- [ ] Verify account-disabled status persists after restart.
- [ ] Inspect the administrative audit log for account creation/disable events.
- [ ] Keep the disposable data directory out of Git; never commit real or demo patient records.

## Evidence to retain for the project review

- Screenshot or terminal capture of the successful build.
- Full CTest summary showing the actual test count and result.
- Short screen recording or screenshots of one successful patient, appointment, and billing flow.
- A screenshot of the duplicate appointment rejection.
- A screenshot of access denial for a role-restricted module.
- Note any untested scenario or failure rather than marking it passed.
